# PR draft

Produce one thing: an HTML preview of a PR description for the work in the current working tree. The Markdown body sits beside it for pasting into GitHub.

This skill reads only. It creates no branch, commit, push, or pull request, and edits nothing on GitHub. The user does those steps themselves with the draft in hand.

A draft describes unfinished work. Half-built features, missing tests, TODO comments, uncommitted files, and failing checks are the expected state, and the description records them. The user's invocation is the go signal: describe the tree as it is and render.

Never add Claude Code, Anthropic, or "generated by" attribution to the title or the body.

## 1. Gather the material

Describe the whole working tree, committed or not.

```sh
BASE=$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name 2>/dev/null \
  || git symbolic-ref --short refs/remotes/origin/HEAD | sed 's|origin/||')
git fetch origin "$BASE" --quiet 2>/dev/null
git log --no-merges --format='%s%n%b' "origin/$BASE..HEAD"      # committed
git diff --stat "origin/$BASE"                                    # committed + uncommitted, one view
git diff "origin/$BASE"
git status --porcelain --untracked-files=all                      # not committed yet
```

`git diff origin/$BASE` (two dots, no `HEAD`) compares the base to the working tree, so staged, unstaged, and committed changes all appear once. Read untracked files directly. On the default branch itself, or with no remote, diff against the last pushed commit or `HEAD~1` and say which you used. When nothing has changed, report that and stop.

Look for the _why_, not just the _what_. In order of preference:

1. An issue number in a commit message or the branch name - read it with `gh issue view <n>` when `gh` is authenticated.
2. A spec, plan, ticket, or ADR file added or touched by the diff.
3. Anything the user passed as an argument.
4. The conversation, if this session did the work.

The diff tells you what changed. Only these tell you why, and the why is the half a reviewer cannot reconstruct. When none of the four exists, infer the why from the code and mark it as inferred; do not ask for it.

### Incomplete work

Judge state from evidence, and record it rather than asking about it:

- Tests absent or failing: say so in Testing, with the failing command's decisive line.
- Features half-built, TODO or FIXME markers, stubs: list what remains under Changes as a **Remaining** bullet list.
- A dependency on another PR or branch: name it in What & why.
- Uncommitted or untracked files: mention them in Testing so the reader knows the description runs ahead of the branch.

Questions about whether the work is "ready" have one answer: it is a draft. Reserve Open questions for decisions a reviewer must make, such as a choice between two designs the code leaves open.

If the diff contains what looks like a secret, key, or token, leave it out of the body and name the file in your report.

## 2. Write the body

**The repository's PR template defines the draft's structure.** Read its `pull_request_template` file or `PULL_REQUEST_TEMPLATE/` directory in the repository root, `.github/`, or `docs/`, including uppercase filename variants. If several templates exist, use the one specified by the user or repository instructions; otherwise choose the one whose name or content fits the change best and name the choice in your report.

Fill the selected template in place, preserving its headings, section order, checklists, tables, and required prompts. Tick a checkbox only when you verified the thing. Before rendering, compare the completed body against the template to ensure every required section is retained.

**If there is no template**, fill [assets/body.md](assets/body.md). Replace its guidance with the actual description and remove Open questions when empty. Use fenced code blocks for commands and code worth copying.

Wrap the body in markers, so a later tool can find the generated block once it is on GitHub:

```md
<!-- pr-draft:start -->

...generated body...
<!-- pr-draft:end -->
```

Write it to a new file such as `/tmp/pr-body-<branch>.md`.

## 3. Write the title

Match the repo. Do not impose a convention it does not use:

```sh
gh pr list --state all --limit 20 --json title -q '.[].title' 2>/dev/null || git log --format=%s -20
```

If those titles are Conventional Commits (`feat:`, `fix:`), follow suit. If they are plain imperative sentences, write one of those. With nothing to go on, default to Conventional Commits. Keep it under 70 characters and describe the change, not the activity: "Cache the resolved config" beats "Changes to config handling".

## 4. Render

Run the bundled `preview` command with the body file and title. Resolve the executable relative to this skill's directory, even when working in another repository:

```sh
<skill-directory>/preview /tmp/pr-body-<branch>.md --title "<title>" --output /tmp/pr-preview-<branch>.html
```

Choose an unused output path; the command preserves existing files. It requires Python 3 and a one-time `pnpm install` in this skills repository to install the renderer. It prints the generated file's absolute path and opens it in the default browser. If opening fails, report that and provide the path.

The preview renders the whole description as HTML in [assets/preview.html](assets/preview.html), with headings, lists, tables, links, and a copy button on each code block. The markers stay in the Markdown and are invisible in the rendered page. Marked renders Markdown and DOMPurify sanitizes the HTML. Both libraries and the sibling [Geist](../geist/SKILL.md) token and type CSS are embedded, so rendering works offline in light and dark themes. Fonts load from Google Fonts with local fallbacks. Read the Geist skill before changing the preview's styling.

Omitting the body path previews the repository's raw template unfilled; the command searches from the current Git repository, or `--repo <path>`, and falls back to the bundled template when none exists.

## 5. Report

Give the user, in this order:

1. The HTML path.
2. The Markdown body path, ready to paste into `gh pr create --draft --body-file <path>` or the GitHub form.
3. The title.
4. Files the description covers that are not committed or pushed yet.
5. Anything inferred or left out (the why, a secret, a template choice).

Stop there. Creating the branch, committing, pushing, and opening the PR are the user's steps.
