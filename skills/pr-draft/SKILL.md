# PR draft

One command for both halves of a PR's life: open it as a draft, then keep its description current as the branch grows.

A draft is the home of unfinished work. Half-built features, missing tests, TODO comments, and failing checks are the expected state, and the description records them. The user's invocation is the go signal: describe the branch as it is and proceed. The only reasons to stop are in **Stop and ask** at the end.

Never add Claude Code, Anthropic, or "generated by" attribution to the title, the body, or any commit. Not in a footer, not in a trailer.

## 1. Check the ground

```sh
git rev-parse --abbrev-ref HEAD
gh auth status
gh pr view --json number,isDraft,title,url,state 2>/dev/null
```

`gh` reads the host from the repo's remote, so GitHub Enterprise needs nothing special. If `gh auth status` does not list that host, stop and tell the user to run `gh auth login --hostname <host>`. Do not attempt the login yourself.

If `gh pr view` returns an open PR, go to **Update**. Otherwise go to **Create**. When several open PRs match the branch, take the most recently updated one and name the others in your report.

**On the default branch:** move the work to a feature branch named after the change (kebab-case, under 40 characters), then continue. Uncommitted changes follow a `git switch -c <name>`. Local commits ahead of `origin/<default>` come along too: after creating the branch, reset the default branch back to its remote with `git branch -f <default> origin/<default>`, and say you did so.

## 2. Gather the material

Describe the whole working tree, committed or not. The PR body is a description of the work; the push decides how much of it is visible on GitHub yet.

```sh
BASE=$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)
git fetch origin "$BASE" --quiet
git log --no-merges --format='%s%n%b' "origin/$BASE..HEAD"      # committed
git diff --stat "origin/$BASE"                                    # committed + uncommitted, one view
git diff "origin/$BASE"
git status --porcelain --untracked-files=all                      # what is not committed yet
```

`git diff origin/$BASE` (two dots, no `HEAD`) compares the base to the working tree, so staged, unstaged, and committed changes all appear once. Read untracked files directly. Note which files are uncommitted; the report and the Testing section mention them, the description does not otherwise treat them differently.

Look for the _why_, not just the _what_. In order of preference:

1. An issue number in a commit message or the branch name - read it with `gh issue view <n>`.
2. A spec, plan, ticket, or ADR file added or touched by the diff.
3. Anything the user passed as an argument.
4. The conversation, if this session did the work.

The diff tells you what changed. Only these tell you why, and the why is the half a reviewer cannot reconstruct. When none of the four exists, infer the why from the code and say it is inferred; do not ask for it.

### Incomplete work

Judge state from evidence, and record it rather than asking about it:

- Tests absent or failing: say so in Testing, with the failing command's decisive line.
- Features half-built, TODO or FIXME markers, stubs: list what remains under Changes as a **Remaining** bullet list.
- A dependency on another PR or branch: name it in What & why.

Questions about whether the work is "ready" have one answer: it is a draft. Reserve Open questions for decisions a reviewer must make, such as a choice between two designs the code leaves open.

## 3. Write the body

**The repository's PR template defines the draft's structure.** Before writing the body, read its `pull_request_template` file or `PULL_REQUEST_TEMPLATE/` directory in the repository root, `.github/`, or `docs/`, including uppercase filename variants. If several templates exist, use the one specified by the user or repository instructions; otherwise choose the one whose name or content fits the change best and name the choice in your report. Where the repository inherits an organization template, use that before the bundled fallback.

Fill the selected template in place, preserving its headings, section order, checklists, tables, and required prompts. Tick a checkbox only when you verified the thing. Keep the same structure in the HTML preview and the submitted PR body; Geist supplies presentation only. Before previewing or publishing, compare the completed body against the selected template to ensure every required section is retained.

**If there is no template**, fill [assets/body.md](assets/body.md). Replace its guidance with the actual description and remove Open questions when empty. Use fenced code blocks for commands and code worth copying.

Wrap whatever you produce in markers:

```md
<!-- pr-draft:start -->

...generated body...
<!-- pr-draft:end -->
```

### Local preview

When the user asks to preview the description, run the bundled `preview` command with the body file and title. Resolve the executable relative to this skill's directory, even when working in another repository:

```sh
<skill-directory>/preview /tmp/pr-body-new.md --title "<title>" --output /tmp/pr-preview.html
```

For an actual draft, pass the completed body that follows the selected repository template. Omitting the body path previews the local repository template without filling it; the command searches from the current Git repository, or `--repo <path>`, and falls back to the bundled template only when no local template exists. It reports multiple candidates so you can pass the chosen template explicitly. Pass an inherited organization template explicitly as well.

Choose an unused output path; the command preserves existing files. It requires Python 3 and a one-time `pnpm install` in this skills repository to install the renderer. It prints the generated file's absolute path and automatically opens it in the default browser. If opening fails, report that and provide the path.

The preview renders the whole description as HTML in [assets/preview.html](assets/preview.html), with headings, lists, tables, links, and a copy button on each code block. Managed Block markers remain in the Markdown and are invisible in the rendered description. Marked renders Markdown and DOMPurify sanitizes the HTML. Both libraries and the sibling [Geist](../geist/SKILL.md) token and type CSS are embedded in the output, so rendering works offline in light and dark themes. Fonts load from Google Fonts with local fallbacks. Read the Geist skill before changing the preview's styling.

The HTML is a local companion; the Markdown body remains the input to `gh`. A preview-only request needs nothing committed or pushed, and ends after producing the HTML.

## 4. Write the title

Match the repo. Do not impose a convention it does not use:

```sh
gh pr list --state all --limit 20 --json title -q '.[].title'
```

If those titles are Conventional Commits (`feat:`, `fix:`), follow suit. If they are plain imperative sentences, write one of those. If the repo is empty of PRs, default to Conventional Commits. Keep it under 70 characters and describe the change, not the activity: "Cache the resolved config" beats "Changes to config handling".

## Create

A PR needs at least one commit on the branch. When the branch has none, commit the working tree yourself: stage everything `git status` lists, skip files that look like secrets or build output, use a message in the repo's commit convention, and report the hash. When commits already exist, push them as they are and leave uncommitted edits alone; the description covers them and the report says which files are still local.

```sh
git push -u origin HEAD
gh pr create --draft --base "$BASE" --title "<title>" --body-file <file>
```

Write the body to a temp file rather than passing it inline - `--body` mangles multi-line markdown.

Then print the PR URL. Say it is a draft and that you did not mark it ready. List any files the description covers that are not on GitHub yet.

Never run `gh pr ready`, `gh pr merge`, or request reviewers unless the user asks in this session.

## Update

The body is jointly owned: the marked block is yours, everything outside it belongs to whoever typed it.

```sh
gh pr view --json body -q .body > /tmp/pr-body.md
```

1. **Markers present** - regenerate only the text between them from the current diff. Leave every byte outside them untouched.
2. **Markers absent** (a human opened this PR by hand) - do not rewrite their description. Append your block at the end, with the markers, and say so.
3. Update the title only if the branch's purpose genuinely changed. A title a human edited stays.
4. **PR already marked ready for review** - update the block the same way. Say in the report that the PR is ready, not draft, so the user knows reviewers may see the change.

```sh
gh pr edit --body-file /tmp/pr-body-new.md
```

Push any unpushed commits first. Uncommitted edits stay local; the description covers them and the report names them.

## Stop and ask

- The diff contains what looks like a secret, key, or token.
- The working tree and the branch have no changes relative to base, so there is nothing to describe.
- `gh` is not authenticated for the remote's host.
