# PR draft

One command for both halves of a PR's life: open it as a draft, then keep its description current as the branch grows.

Never add Claude Code, Anthropic, or "generated by" attribution to the title, the body, or any commit. Not in a footer, not in a trailer.

## 1. Check the ground

```sh
git rev-parse --abbrev-ref HEAD          # must not be the default branch
gh auth status                            # must be authed for this remote's host
gh pr view --json number,isDraft,title,url 2>/dev/null
```

`gh` reads the host from the repo's remote, so GitHub Enterprise needs nothing special - but if `gh auth status` does not list that host, stop and tell the user to run `gh auth login --hostname <host>`. Do not attempt the login yourself.

If `gh pr view` returns a PR, go to **Update**. Otherwise go to **Create**.

If HEAD is the repo's default branch, stop. Ask the user to branch first; do not create one for them.

## 2. Gather the material

Find the base branch:

```sh
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
```

Then read what changed:

```sh
BASE=$(gh repo view --json defaultBranchRef -q .defaultBranchRef.name)
git log --no-merges --format='%s%n%b' "origin/$BASE..HEAD"
git diff --stat "origin/$BASE...HEAD"
git diff "origin/$BASE...HEAD"
```

Look for the _why_, not just the _what_. In order of preference:

1. An issue number in a commit message or the branch name - read it with `gh issue view <n>`.
2. A spec, plan, ticket, or ADR file added or touched by the diff.
3. Anything the user passed as an argument.
4. The conversation, if this session did the work.

The diff tells you what changed. Only these tell you why, and the why is the half a reviewer cannot reconstruct.

## 3. Write the body

**The repository's PR template defines the draft's structure.** Before writing the body, read its `pull_request_template` file or `PULL_REQUEST_TEMPLATE/` directory in the repository root, `.github/`, or `docs/`, including uppercase filename variants. If several templates exist, use the one specified by the user or repository instructions; ask which to use when the choice remains ambiguous. Where the repository inherits an organization template, use that before the bundled fallback.

Fill the selected template in place, preserving its headings, section order, checklists, tables, and required prompts. Leave checkboxes unticked unless you actually verified the thing. Keep the same structure in the HTML preview and the submitted PR body; Geist supplies presentation only. Before previewing or publishing, compare the completed body against the selected template to ensure every required section is retained.

**If there is no template**, fill [assets/body.md](assets/body.md). Replace its guidance with the actual description and remove Open questions when empty. Use fenced code blocks for commands and code worth copying.

Wrap whatever you produce in markers:

```md
<!-- pr-draft:start -->

...generated body...
<!-- pr-draft:end -->
```

### Local preview

When the user asks to preview the description, run the bundled `preview` command with the body file and title. Resolve the executable relative to this skill's directory, even when working in another repository:

```sh
<skill-directory>/preview /tmp/pr-body-new.md --title "<title>" --output /tmp/pr-preview.html
```

For an actual draft, pass the completed body that follows the selected repository template. Omitting the body path previews the local repository template without filling it; the command searches from the current Git repository, or `--repo <path>`, and falls back to the bundled template only when no local template exists. It reports multiple candidates so you can pass the chosen template explicitly. Pass an inherited organization template explicitly as well.

Choose an unused output path; the command preserves existing files. It requires Python 3 and a one-time `pnpm install` in this skills repository to install the renderer. It prints the generated file's absolute path and automatically opens it in the default browser. If opening fails, report that and provide the path.

The preview renders the whole description as HTML in [assets/preview.html](assets/preview.html), with headings, lists, tables, links, and a copy button on each code block. Managed Block markers remain in the Markdown and are invisible in the rendered description. Marked renders Markdown and DOMPurify sanitizes the HTML. Both libraries and the sibling [Geist](../geist/SKILL.md) token and type CSS are embedded in the output, so rendering works offline in light and dark themes. Fonts load from Google Fonts with local fallbacks. Read the Geist skill before changing the preview's styling.

The HTML is a local companion; the Markdown body remains the input to `gh`. A preview-only request ends after producing the HTML, before pushing or creating/updating a PR.

## 4. Write the title

Match the repo. Do not impose a convention it does not use:

```sh
gh pr list --state all --limit 20 --json title -q '.[].title'
```

If those titles are Conventional Commits (`feat:`, `fix:`), follow suit. If they are plain imperative sentences, write one of those. If the repo is empty of PRs, default to Conventional Commits. Keep it under 70 characters and describe the change, not the activity: "Cache the resolved config" beats "Changes to config handling".

## Create

```sh
git push -u origin HEAD
gh pr create --draft --base "$BASE" --title "<title>" --body-file <file>
```

Write the body to a temp file rather than passing it inline - `--body` mangles multi-line markdown.

Then print the PR URL. Say it is a draft and that you did not mark it ready.

Never run `gh pr ready`, `gh pr merge`, or request reviewers unless the user asks in this session.

## Update

The body is jointly owned: the marked block is yours, everything outside it belongs to whoever typed it.

```sh
gh pr view --json body -q .body > /tmp/pr-body.md
```

1. **Markers present** - regenerate only the text between them from the current diff. Leave every byte outside them untouched.
2. **Markers absent** (a human opened this PR by hand) - do not rewrite their description. Append your block at the end, with the markers, and say so.
3. Update the title only if the branch's purpose genuinely changed. A title a human edited stays.

```sh
gh pr edit --body-file /tmp/pr-body-new.md
```

Push any unpushed commits first, so the description matches what is actually on the branch.

## Stop and ask

- The branch has no commits relative to base.
- The diff contains what looks like a secret, key, or token.
- The PR is already marked ready for review - confirm before editing it.
- More than one PR matches the branch.
